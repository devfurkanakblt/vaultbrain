`docs/ARCHITECTURE.md`, `docs/FORMAT-1.0.md`, `docs/AUDIT-SCOPE.md`, and the

## Global constraints

- Read `AGENTS.md` and inspect the current code before changing it. When an existing
  graph is available, use Graphify queries for codebase investigation; update the
  graph after code changes.
- Preserve older vault readability and every committed compatibility fixture.
- Work test-first for behavior changes. Each subphase must be independently
  reviewable and must not rely on a later subphase to restore safety.
- Do not generate production signing material, modify repository secrets, publish a
  release, create a release tag, or push without explicit authorization.
- Never mark external audit, cross-platform validation or real-device acceptance as
  complete based only on mocks or synthetic CI evidence.
- Keep earlier roadmap items traceable. When ownership moves here, annotate the old
  item with its Phase 14 destination; close both only after the new acceptance gate
  passes.
- Avoid parallel implementations of the same protocol behavior. Define one canonical
  owner and make all other surfaces call or verify it.
- Keep passphrases, keys and plaintext vault content out of logs, process arguments,
  configuration, crash journals and unprotected temporary files.

## Phase 14.1 — Complete multi-device sync

The sync and epoch-rotation implementation is present at this baseline. Phase 14.1
is therefore a verification and evidence exercise; it must not introduce a second
sync protocol. Identity rotation starts a new owner epoch and requires explicit
peer re-enrollment. A revoked device retains pre-rotation access but receives no
wrap for later epochs.

### Task 1: Portable workspace-state contract

- [ ] Write a focused design specification for the portable representation of saved
      views, bookmarks and layouts.
- [ ] Decide and document the canonical owner across the TypeScript sync core and the
      Rust-owned `workspace.enc` surface.
- [ ] Define versioning, conflict semantics, causal ordering, size limits and
      fail-closed validation before implementation.
- [ ] Prove that a second device cannot silently lose supported workspace state.

### Task 2: Workspace-state synchronization

- [ ] Review existing cross-device tests and record the parent agent's exact results
      for saved views, bookmarks and layouts; add code only if evidence identifies a
      real gap.
- [ ] Capture local workspace mutations in the encrypted immutable change protocol.
- [ ] Apply valid remote workspace changes to live storage transactionally.
- [ ] Cover concurrent edits, duplicates, replay, malformed payloads, rollback and
      crash recovery.
- [ ] Preserve compatibility with vaults and peers that predate portable workspace
      state.

### Task 3: Desktop-driven device lifecycle

- [ ] Verify owner-controlled desktop enrollment and explicit identity/fingerprint
      verification in the existing implementation and record evidence.
- [ ] Verify owner-controlled revocation and the existing forward-only epoch
      rotation guarantees; preserve the new owner epoch and explicit re-enrollment
      requirement after identity rotation.
- [ ] Verify desktop relay push/pull, bounded operations, cancellation, progress and
      retry behavior in the existing implementation and record evidence.
- [ ] Enforce unlock state, capability scope and user confirmation in the native
      command boundary; do not expose arbitrary URLs, keys or paths to the frontend.
- [ ] Test stale responses, concurrent operations, revoked devices, hostile relay
      data, offline behavior and secret-free error reporting.

### Acceptance gate

- [ ] Two desktop instances can enroll, exchange all supported portable state,
      revoke a device and continue syncing under the new epoch.
- [ ] Notes, canvases, attachments, plugin policy, saved views, bookmarks and layouts
      survive the documented recovery drill.
- [ ] Focused TypeScript, Rust and desktop tests pass on all supported platforms.
- [ ] The external security-audit checkbox remains open until an independent audit is
      actually completed.

## Phase 14.2 — Re-key aftermath

The re-key and identity-rotation paths are present at this baseline. Phase 14.2 is
verification and documentation of their durable behavior, not a permission to
reimplement them. Identity rotation must preserve the new owner epoch and require
clean peer re-enrollment. Lock recovery remains fail-closed: ambiguous lock state
has no override.

### Task 1: Attachment-identity migration design

- [ ] Write and review a dedicated specification before implementation.
- [ ] Enumerate every reference affected by rotating `attachmentId`: attachment
      directories, active canvases, canvas history, derived indexes and sync changes.
- [ ] Define how rotated sync-change IDs rewrite descendant `parent` references while
      preserving a valid causal DAG.
- [ ] Define a multi-device/version-transition rule that prevents peers from deriving
      divergent identities.
- [ ] Define interruption, resume, rollback, space-budget and stale-journal behavior.

### Task 2: Atomic and resumable identity migration

- [ ] Review existing failure-injection evidence at every durable transition and
      record the parent agent's exact results; add code only for a demonstrated gap.
- [ ] Stage and verify the complete rewritten vault before changing live identity.
- [ ] Make replay after interruption idempotent.
- [ ] Fail closed on unknown encrypted artifacts, missing references, symlinks,
      malformed history or an inconsistent change DAG.
- [ ] Verify old and new fixtures, cross-core reads and multi-device compatibility.

### Task 3: Deliberate lock-break path

- [x] Document the command, threat model, owner confirmation and audit record.
- [ ] Distinguish a live lock from a stale or abandoned lock using the strongest
      platform evidence available.
- [x] Refuse ambiguous cases by default with no lock override; recovery is limited
      to the proven same-host dead-process path.
- [ ] Test live-owner refusal, stale-lock recovery, malformed lock metadata, PID reuse,
      concurrent attempts and crash recovery.

### Acceptance gate

- [ ] A fully populated synchronized vault can re-key and rotate affected identities
      without losing content, history, links or DAG validity.
- [ ] Randomly interrupted migrations resume or roll back to a complete vault.
- [ ] A live lock cannot be broken accidentally in the supported threat model.
